Ce que fait le moteur, de bout en bout

Un lanceur d'outils
en bac à sable.

Le moteur KTRX ouvre un fichier .tool, exécute le WebAssembly qu'il contient dans une sandbox fermée, et ne lui donne accès au réseau ou aux fichiers que si le manifeste le déclare et que tu l'as approuvé pour cette exécution. Il ne connaît aucun protocole : il fournit des primitives, les outils font le métier.

01 · Rôle

À quoi il sert

PORTABILITÉ

Un outil, trois systèmes

Un .tool compilé une fois (cible wasm32-wasip2) tourne tel quel sous Windows, Linux et macOS. Le moteur absorbe les différences d'OS : sockets, résolveurs DNS, certificats racines Windows, ICMP.

CONFINEMENT

Rien sans ton accord

L'outil reçoit un contexte WASI vide : pas de socket, pas de disque, pas de variables d'environnement. Tout passe par un seul guichet, host.request, qui contrôle manifeste et approbation à chaque appel.

SÉPARATION

Le moteur reste générique

HTTP, scan de ports, empreintes, CVE : tout ça vit dans les outils. Un test d'architecture fait échouer le build si le runtime se met à contenir http.get, tcp.scan ou un client HTTP.

    06 · Ligne de commande
    
      
    Ce que tu peux lui demander
    
    
    
    
    
      
    ktrx run <outil.tool> [args]
    Exécute l'outil. Les options du moteur (-y, --write-dir, --json, --events) se placent avant le chemin de l'outil, sinon elles sont transmises à l'outil.
    
      
    ktrx run <outil.tool> --help
    Aide générée depuis le manifeste : arguments, obligatoires, exemples.
    
      
    ktrx run --events <outil.tool> …
    Flux NDJSON : {"type":"progress",…} puis {"type":"finished",…}, pour brancher une interface ou un script.
    
      
    ktrx info / describe <outil.tool>
    Métadonnées lisibles, ou le manifeste complet en JSON.
    
      
    ktrx validate <outil.tool>
    Vérifie l'archive, le manifeste et que le composant implémente bien l'interface KTRX.
    
      
    ktrx pack <dossier> -o <K~NOM.tool>
    Assemble manifest.toml et module.wasm en archive.

    08 · Évolution
    
      
    Où en est le moteur
    
      
    Le lot 1 vient d'être livré. Les suivants gardent la même règle : des mécanismes génériques côté hôte, le métier dans les outils.
    
    
    
    
    
      
    Lot 1 · livré
    Fiabilité
    • Erreurs typées error_kind, indépendantes de la langue de l'OS
    • socket.wait : attente groupée
    • Cache des connecteurs TLS
    • Lectures annulables
    • HORUS 1.2.0
    
      
    Lot 2 · proposé
    TLS et sockets
    • socket.starttls (SMTP, IMAP, LDAP…)
    • Diagnostic des poignées de main échouées
    • socket.info, shutdown, options TCP
    • Multicast UDP, ping IPv6
    
      
    Lot 3 · proposé
    Contrôle utilisateur
    • --scope CIDR / domaines imposé par l'hôte
    • --rate, quotas de connexions
    • --proxy SOCKS5 / HTTP
    • --trace : journal réseau
    
      
    Lot 4 · plus tard
    Extensions
    • socket.listen sous permission dédiée
    • Canal binaire WIT 1.1, sans Base64
